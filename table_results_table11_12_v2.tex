% Table 11+12 analogue for submodel V2: MILP vs WFBF-grid vs beam search
% on the single-bin size sweep. Two tables, matching the paper's own
% split: Table 11 (n = 18-90, ten instances per size) has all three
% methods; Table 12 (n = 100-200) has WFBF-grid and BS only.
% Data from results_table11_12_V2/.
%
% WHY TABLE 12 HAS NO MILP COLUMN: the V2 MILP's empty-packing defect
% (see the Table 11 notes below) is confirmed at n=100 and expected to
% persist across n=100-200, so the MILP was deliberately not run for
% this range (slurm_t12_nomilp.sbatch) rather than spend cluster time
% reproducing a known-bad result 110 more times. Once the defect is
% root-caused and fixed, the MILP column can be filled in from
% slurm_t11t12.sbatch with --solver milp.
%
% Layout follows table_results_table13_v2.tex: objective (1) with the
% running time, for each method. LOWER OBJECTIVE IS BETTER. Every figure
% is the mean over the ten instances of that size.
%
% Three things to keep in mind when reading these tables:
%
%  1. The MILP column (Table 11 only) is degenerate for n >= 27. On
%     those 17 sizes Gurobi returns the EMPTY packing (no item placed,
%     no bin opened) in under 9 s and reports it OPTIMAL with a zero
%     gap, so the objective is exactly 1.0. Beam search finds verified
%     V2-feasible packings of objective 0.04-0.14 on the very same
%     instances, so the MILP's optimality claim cannot be correct. This
%     is the SAME defect already documented for the multiple-bin grid in
%     table_results_table13_v2.tex; it was previously thought to be
%     specific to multiple bins, but it reproduces here with a single
%     bin once n is large enough, so the trigger is instance size (or a
%     property that correlates with it), not bin count. For n = 18-26
%     the MILP behaves normally, hitting TIME_LIMIT with a non-trivial
%     packing. The column is reported as measured and is a defect to
%     investigate, not a result about the model of the paper.
%
%  2. For the n = 18-26 rows, where the MILP hits TIME_LIMIT rather than
%     the degenerate optimum, its packings show verifier violations
%     (63-78 per size, all "disallowed rotation" or "floating item").
%     Every one of these comes from a TIME_LIMIT run; all 140 OPTIMAL
%     runs elsewhere in Table 11 have zero violations. This looks like
%     a floating-point tolerance issue reading Gurobi's incumbent at an
%     unconverged cutoff rather than a genuine infeasibility, but it has
%     not been root-caused, so it is reported rather than silently
%     corrected.
%
%  3. WFBF-grid's violation count keeps climbing with n (11 at n=100 up
%     to 23 at n=200), consistent with its behaviour throughout this
%     paper: it enforces neither the centre-of-mass nor the
%     load-bearing constraints, so more items simply means more chances
%     to violate one. Beam search remains at 0 violations across every
%     size in both tables.
% =====================================================================
